### 2장 · 기존 프로젝트는 어떤 서비스인가

대본 배분: 18초

**발표 대본**

기존 프로젝트는 서비스 이름과 장애 증상을 입력하면 모니터링 지표와 대응 매뉴얼을 조회해 진단 보고서를 만드는 AI 에이전트입니다.

**구현 설명·질문 대비**

- 기존 프로젝트는 수업에서 제공한 서비스 장애 진단 에이전트다. FastAPI 서버, LangGraph 그래프, MCP Tool·Resource·Prompt, Vue 채팅 화면, SQLite 대화 이력이 이미 있다.
- 원래 흐름은 route → plan → gate → research → replan_check → analysis → write → validate → finalize다. 일반 대화는 조사 파이프라인을 건너뛴다.
- 이번 개선에서 실제로 검증한 모델은 Ollama의 qwen3:0.6b/8b다. 모니터링은 교육용 모의 데이터이며 실제 운영 로그·서버 조치는 없다. 기존 기반 전체를 새로 개발했다고 말하지 않는다.

### 4장 · 사용 기술과 적용 방법

대본 배분: 23초

**발표 대본**

MCP에 검색 도구를 추가하고 RAG로 문서를 찾습니다. 그래프 처리를 모듈로 분리하고 검색기를 주입해 실제 MCP와 고정 평가를 교체합니다. 분기 테스트와 동일 입력 평가로 확인했습니다.

**구현 설명·질문 대비**

- MCP: mcp_server.py의 search_runbooks Tool을 추가했다. retrieval.py의 MCPRunbookSearch가 이 Tool을 호출하고, research.py가 검색 결과의 URI로 기존 MCP Resource 원문을 읽는다. MCP 서버 분리나 기존 Tool·Resource 체계를 새로 구현한 성과로 주장하지 않는다.
- RAG: runbook 6개 본문·한영 증상 메타데이터와 서비스별 활성 알림을 bge-m3로 임베딩한다. SQLite에 캐시한 정규화 벡터의 코사인 유사도를 계산하고 임계값 0.35, 후보 2개 중 첫 원문을 연결한다. 대규모 벡터 DB나 ANN 검색을 구현한 것은 아니다.
- LangGraph·모듈화: 기존 그래프 처리를 대상·수집·검색·보고·검증 모듈로 분리하고 범위·상태별 분기를 연결했다. 독립적인 전문 Multi-Agent 서브그래프를 추가한 구현은 아니다.
- 의존성 주입: 기존 SupervisorDeps에 searcher를 추가했다. 연구 노드는 검색 구현을 직접 만들지 않고 주입된 검색기를 우선 사용한다. 실제 앱은 MCP 검색 Tool, 평가·단위 테스트는 고정 데이터 검색 어댑터를 연결한다.
- 단위 테스트 31개와 실제 모델 고정 입력 20건은 목적이 다르다. 전자는 대상 추출·수치 변조·부분 실패·시간 제한 등의 코드 분기, 후자는 실제 호출·문서 선택·응답 상태·시간을 확인한다. 실제 MCP·SSE·UI 검증은 별도로 수행했다.
- 교수님이 나열한 기술은 예시이며 전부 추가하라는 필수 목록으로 쓰여 있지 않다. 기존 LangSmith traceable 장식은 유지하지만 새 추적 연결·대시보드 분석을 검증한 성과에는 포함하지 않는다. 전문 Multi-Agent 확장도 성과로 표기하지 않는다.

### 12장 · 개선 2 후 · 미등록이면 등록 이름을 다시 묻는다

대본 배분: 11초

**발표 대본**

등록 목록과 먼저 대조합니다. 미등록이면 조회와 보고 생성을 건너뛰고, 다른 서비스로 바꾸지 않고 이름을 확인합니다.

**구현 설명·질문 대비**

- select_targets가 서비스처럼 보이지만 등록 목록에 없는 billing-service를 unknown에 넣는다. targets가 비면 plan_node가 보고 모델의 계획을 호출하지 않고, 모니터링 수집도 비어 있다.
- 문서·관측이 없으면 write_node가 보고 생성을 생략하고 render_report가 등록 이름 확인 안내를 만든다. 안내는 LLM이 작성한 진단 성공으로 세지 않는다.
- 등록·미등록 혼합 요청은 등록된 대상은 조사하고, 미등록 대상은 따로 표시한다.

### 18장 · 개선 4 후 · 조회 결과와 매뉴얼 원문으로 보고했다

대본 배분: 18초

**발표 대본**

모델은 수치·문서·절차 번호를 JSON으로 고르게 했습니다. 코드가 근거와 대조하고, 통과한 절차를 원문으로 출력해 조치 조건이 바뀌지 않게 했습니다.

**구현 설명·질문 대비**

- StructuredReportLLM은 sections JSON으로 서비스 이름·CPU·메모리·runbook_id·step_ids·cause_confirmed만 출력하도록 한다.
- validate_draft는 누락·중복·범위 밖 서비스, 잘못된 수치, 없는 문서·절차, 원인 확정, 자유 필드를 거절한다.
- 검증 후 render_report가 선택된 절차의 원문을 가져온다. 원문의 90% 초과·지속 등의 조건을 모델이 바꿔 쓰지 않는다.
- 모든 자유 문장의 의미를 판정하거나 현재 조치 조건 충족을 자동 판단하는 기능은 아니다. 실제 조치도 실행하지 않는다.

### 20장 · 대화 개선 후 · 사용자 이름을 올바르게 답한다

대본 배분: 8초

**발표 대본**

이름은 사용자 역할의 선언에서만 읽습니다. 이름 질문과 비서의 자기소개는 제외합니다. 이 부분은 계획 외에 보완한 대화 처리입니다.

**구현 설명·질문 대비**

- remembered_name은 history에서 role=user인 메시지와 현재 입력만 읽고, '제 이름은 ...입니다' 같은 선언형만 추출한다. assistant 발화와 '이름이 뭐였죠' 질문은 이름 선언으로 보지 않는다.
- 추출한 이름의 별도 메모리 DB를 새로 만든 것이 아니다. 기존 SQLite 대화 이력을 활용하고 같은 대화의 최근 사용자 선언을 읽는다.
- 서버 재시작 뒤 같은 DB·thread의 이름 응답도 별도 기록으로 검증했다. 캡처 자체가 재시작 과정을 보여주는 것은 아니다.

### 21장 · 추가 1 · 증상에 맞는 매뉴얼을 검색한다

대본 배분: 17초

**발표 대본**

첫 추가 기능은 RAG입니다. 서비스별 알림과 매뉴얼을 bge-m3로 벡터화해 검색하고, 선택한 문서는 MCP로 원문을 읽습니다.

**구현 설명·질문 대비**

- 기존 6개 runbook 본문과 한·영 증상 메타데이터를 bge-m3로 임베딩하고 SQLite에 캐시한다. 문서 변경 시 digest를 확인해 인덱스를 갱신한다.
- 서비스별 활성 알림을 임베딩하고 정규화한 벡터의 코사인 유사도로 검색한다. 임계값 0.35, 후보 상위 2개 중 첫 문서를 실제 원문과 연결한다.
- 검색기는 기존 SupervisorDeps에 추가한 searcher로 주입한다. 실행 시 MCP 검색 Tool을 사용하고 고정 데이터 평가에서는 검색 어댑터를 사용한다.
- 유사도 0.673은 정답 확률이 아니다. 문서 6개 전수 비교이며 대규모 ANN 검색이나 운영 부하 검증은 하지 않았다.

### 22장 · 추가 2 · 답변에 사용한 근거를 화면에 표시한다

대본 배분: 12초

**발표 대본**

두 번째는 근거 화면입니다. 실제 조회한 서비스와 수치, 참고 매뉴얼을 표로 보여주고 확인하지 못한 항목도 함께 표시합니다.

**구현 설명·질문 대비**

- evidence_payload는 실제 collected에서 서비스·관측·runbook·미등록·미확인·오류를 구성한다. server.py가 FinalAnswer.evidence에 담고 web_chat.html이 그 객체로 표를 그린다.
- 모델이 출력한 출처 문자열을 그대로 화면 근거로 쓰지 않는다. 정상 web은 문서 없음, auth는 지연 매뉴얼·유사도가 표시된다.

### 23장 · 추가 3 · 같은 질문의 결과를 자동 비교한다

대본 배분: 13초

**발표 대본**

세 번째는 자동 비교입니다. 같은 질문과 고정 지표로 전후 실행하고 호출·문서·시간을 집계합니다. 단위 테스트 서른한 개도 통과했습니다.

**구현 설명·질문 대비**

- 평가 정의 cases.json의 expected_targets·expected_runbooks와 실제 calls·elapsed_seconds를 대조한다. 대상 수집은 서비스 수, 범위 일치는 대상 집합이 같은 질문 수, 문서 Top-1은 정답 문서가 하나인 질문만 계산한다.
- 고정 데이터 그래프 평가 20건과 실제 MCP·SSE·UI 검증은 구분한다. 이 보고서는 보존된 전후 결과 JSON을 집계한 것이며 새 20건 벤치마크를 실행한 것은 아니다.
- 단위 테스트 31개는 대상 추출·검증·부분 실패·시간 제한·이름 역할 등의 분기다. 20건 실제 모델 평가와 다른 검증이다.

### 24장 · 개선 전후 측정 결과

대본 배분: 25초

**발표 대본**

필요한 서비스 수집은 열일곱에서 스무 개로, 조회 범위 일치는 열다섯에서 스무 문항으로 늘었습니다. 매뉴얼 선택도 개선됐습니다. 같은 열여섯 문항의 시간 중앙값은 삼십오 점 구사 초에서 사 점 사오 초입니다. 생성 설정도 함께 바꾼 결과입니다.

**구현 설명·질문 대비**

- 등록 대상 수집 17/20→20/20은 서비스 수다. D05 payments, D06 cache, D07 auth 누락을 보완했다. 조회 범위 일치는 15/20→20/20이며 auth 대체 조회 2건도 포함한다.
- 단일 정답 문서 11/12→12/12는 D07의 db-down을 high-latency로 바꾼 결과다. 같은 모델·고정 지표·질문을 사용했다.
- 양쪽 완료한 동일 16건 중앙값은 35.936→4.454초다. 네트워크 전송·UI 표시·워밍업·인덱스 구축은 제외한다. 생성 설정·분기·출력 형식도 바뀌어 RAG만의 효과가 아니다.
- 개선 20건은 검증13·관측/확인안내4·대화2·검증실패안내1이다. 응답 완료가 전체 답변의 정확도100%라는 뜻은 아니다. 이후 화면·안내 문구 수정 뒤 전체 시간은 재측정하지 않았다.
- 그래프는 보존된 전후40개 실행 기록에서 직접 재집계했다. 세 수집·선택 지표는 개수, 시간은 초 단위이며 각 분모를 제목과 데이터 레이블에 표시한다. 원점을0으로 둔 막대이며 기준을 그래프 장에 합쳤다.
- 등록 대상 수는 필요한 서비스와 실제 조회 목록을 대조한다. 범위 일치는 실제 대상 집합과 기대 대상 집합이 같아야 한다. 문서는 단일 정답 질문의 첫 조회를 대조한다. 별도 기준 슬라이드 대신 그래프 아래에 기준을 표시한다.

### 25장 · 한계와 다음 개선 방향

대본 배분: 18초

**발표 대본**

문서 여섯 개와 모의 지표라 운영 성능으로 일반화할 수 없습니다. 검색은 지연·오검색을 더하고 원문 출력은 설명을 제한합니다. 다음은 실제 로그와 독립 질문으로 검증하겠습니다. 감사합니다.

**구현 설명·질문 대비**

- 문서 6개·모의 지표·관측한 시험 세트이므로 독립 질문과 실제 운영 자료가 필요하다.
- 실제 로그·시계열·서비스 의존 관계 수집, 복합 장애 검색과 독립 평가가 다음 과제다. 자동 복구를 구현했다고 말하지 않는다.
- 검색·임베딩은 처리 부담과 오검색을 더하고, 원문 출력은 자유로운 종합 설명을 제한한다.

## 예상 질문

- **개선 항목은 무엇인가?** 대상 누락 방지, 미등록·미명시 대상 확인, 상태별 매뉴얼 선택, 수집 근거와 답변 검증의4개다. RAG 검색·근거 화면·비교 평가는 추가3개다.
- **모델이 최종 문장을 모두 쓰나?** 모델은 서비스·수치·문서·절차 번호를 선택한다. 코드가 근거와 대조하고 검증된 절차를 매뉴얼 원문으로 표시한다.
- **어떤 기술을 직접 바꿨나?** 기존 MCP에 검색 Tool을 추가했다. RAG 검색·상태 분기·모듈화를 구현하고 기존 의존성 주입에 검색기를 추가했다. 전문 Multi-Agent 확장과 새 LangSmith 분석은 성과에 포함하지 않는다.
- **그래프 기준은 무엇인가?** 대상 수집은 필요한 등록 서비스와 실제 조회 목록의 교집합, 범위 일치는 대상 집합의 일치, 문서는 단일 정답 질문의 첫 선택이다. 시간은 전후 모두 완료한 같은16문항의 중앙값이다.
- **시간 단축이 RAG 때문인가?** 생성 설정·출력 형식·분기도 함께 변경했다. RAG 단독 효과로 해석하지 않는다.
- **왜 기준 화면이 없어졌나?** 결과 그래프와 중복되므로 기준을 그래프 하단과 이 노트로 합쳤다. 실제 질문·응답과 비교 평가 보고서 캡처는 앞의 기능 설명에서 제시한다.
