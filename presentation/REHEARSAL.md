# 발표 대본과 상세 해설

## 5분 발표용 본문

문제 → 구현 방법 → 같은 질문의 결과 순서로 설명한다. 아래 문장은 PPT의 발표자 노트와 같다. 같은 사례의 연속 캡처는 한 설명으로 이어서 말한다.

배분 합계는294초이며 실제 낭독을 측정한 시간은 아니다. 발표용 본문은 공백 제외1,750자다. 기술명·화면 전환에 걸리는 시간을 포함해 실제 리허설로 확인한다. 상세 해설은 본문에 모두 더해 읽는 분량이 아니다.

### 도입 · 1장~3장

**1장**  안녕하세요. 실습 일 번, 베이스 프로젝트 개선을 선택한 이진형입니다.

**2장**  베이스 프로젝트는 서비스 이름과 증상을 입력하면, 모니터링 지표와 대응 매뉴얼을 조회해 진단 보고서를 만드는 에이전트입니다. 다만 교육용 모의 지표를 사용하며 서버를 실제로 복구하는 프로그램은 아닙니다.

**3장**  예제 질문을 실행해 보니, 답변이 그럴듯해도 요청한 대상을 조사하지 않거나 근거 없는 분석을 붙이는 문제가 있었습니다. 그래서 조사 대상과 답변 근거가 일치하도록 네 가지를 고쳤습니다. 개선 사례부터 보겠습니다.


### 개선 1 · payments와 cache의 조사 누락 · 4장~6장

**4장**  첫 번째는 조사 누락입니다. 결제와 캐시의 공통 원인을 물었지만, 수집된 사실에는 결제만 있습니다. 그런데 답변은 캐시까지 포함해 트래픽 급증을 추정했습니다.

**5장**  기존에는 실제 조회 목록이 모델의 계획에 의존했습니다. 이를 바꿔 요청에서 등록 서비스를 모두 찾고, 그 목록으로 조회 작업을 다시 구성했습니다. 화면처럼 두 서비스를 각각 조회합니다.

**6장**  결과도 각각 보여줍니다. 다만 두 서비스가 저하됐다는 사실만으로 공통 원인을 알 수는 없어, 공유 로그와 의존 관계는 미확인으로 남겼습니다.


### 개선 1 · gateway와 payments에도 같은 처리 적용 · 7장~9장

**7장**  같은 문제가 게이트웨이에서 결제로 가는 타임아웃 질문에도 있었습니다. 기존에는 게이트웨이만 조회했습니다.

**8장**  개선 후에는 요청을 보내는 쪽과 받는 쪽을 모두 조사합니다.

**9장**  네트워크 알림과 결제의 CPU 문제를 각각 보여주되, 둘의 인과관계까지 확인했다고 답하지는 않습니다.


### 개선 2 · 미등록 서비스의 임의 대체 제거 · 10장~11장

**10장**  두 번째는 다른 서비스로의 대체입니다. 빌링을 물었는데, 실제로는 인증 서비스인 auth를 조회했습니다.

**11장**  미등록 이름을 auth로 바꾸던 기본 처리를 제거했습니다. 등록 목록에 없으면 조회를 진행하지 않고 이름을 확인합니다. 잘못된 대상의 진단을 만드는 일을 막은 것입니다.


### 개선 2 · 서비스 이름이 없는 요청 · 12장~13장

**12장**  서비스 이름 없이 로그인 지연만 말해도 기존에는 auth를 가정했습니다.

**13장**  이 경우도 대상부터 질문하도록 바꿨습니다. 대상을 추정하는 편의성보다 정확한 조회를 우선한 정책입니다.


### 개선 3 · 관측 상태에 맞는 매뉴얼 선택 · 14장~15장

**14장**  세 번째는 매뉴얼 선택입니다. web은 정상이고 알림도 없는데 DB 장애 매뉴얼이 붙었습니다. 함께 요청한 auth도 빠졌습니다.

**15장**  조회한 상태와 알림으로 정상, 장애, 정보 부족을 먼저 나눴습니다. 정상인 web은 검색을 생략하고, auth는 실제 지연 알림으로 해당 매뉴얼을 찾습니다. 질문에 적힌 증상만으로 장애를 정하지 않도록 바꿨습니다.


### 개선 4 · 답변을 수집 근거와 대조 · 16장~17장

**16장**  네 번째는 답변 검증입니다. CPU 질문에 로그 분석 결과 특이 패턴이 없다고 했지만, 실제로는 로그를 조회하지 않았습니다.

**17장**  이제 모델은 서비스와 수치, 문서와 절차 번호를 JSON으로 선택합니다. 코드가 수집 근거와 대조한 뒤, 검증된 절차를 매뉴얼 원문으로 보여줍니다. 따라서 조치의 조건을 보존할 수 있지만, 자유로운 설명은 줄어듭니다.


### 대화 처리 보완 · 18장~19장

**18장**  대화 테스트에서는 사용자 이름 민수를 비서의 이름처럼 답한 문제도 있었습니다.

**19장**  사용자가 직접 밝힌 이름만 읽도록 보완해, 같은 두 번의 대화에서 민수라고 답하게 했습니다.


### 개선에 적용한 기술 · 20장

**20장**  이 개선은 기존 LangGraph 흐름에서 대상 확인, 수집, 검증을 모듈로 나눠 적용했습니다. 여기에 MCP 검색 도구를 추가했습니다. 검색기는 의존성 주입으로 교체해 실제 실행과 고정 데이터 평가를 같은 처리 흐름으로 시험합니다. 다음은 추가 기능 세 가지입니다.


### 추가 1 · RAG 매뉴얼 검색 · 21장

**21장**  첫째는 RAG 검색입니다. 서비스별 알림과 매뉴얼을 bge-m3로 임베딩해 비교하고, 선택한 문서는 MCP로 원문을 읽습니다. 디스크 공간 부족 사례에서 해당 매뉴얼이 연결됩니다. 유사도 영 점 육칠삼은 검색 점수이며 정답 확률은 아닙니다.


### 추가 2 · 근거 화면 · 22장

**22장**  둘째는 근거 화면입니다. 모델이 쓴 설명을 그대로 출처로 삼지 않고, 실제 수집 객체에서 서비스와 수치, 문서를 표시합니다. 사용자는 정상 web에는 문서가 없고 auth에는 지연 문서가 붙은 이유를 확인할 수 있습니다.


### 추가 3 · 회귀 테스트와 전후 비교 · 23장

**23장**  셋째는 회귀 테스트와 전후 비교입니다. 같은 질문 스무 개와 같은 모의 지표를 넣고, 실제 조회 대상과 선택 문서를 정답 목록에 대조합니다. 이 화면은 그 실행 기록입니다. 별도로 단위 테스트 서른한 개로 핵심 분기를 확인했습니다.


### 측정 결과 · 24장

**24장**  서비스 조회는 스무 건 중 열일곱 건에서 스무 건으로, 조회 대상이 일치한 질문은 열다섯 개에서 스무 개로 늘었습니다. 단일 정답 매뉴얼은 열두 개 중 열한 개에서 열두 개가 맞았습니다. 진단 전체의 정확도가 아니라 대상과 문서 선택의 평가입니다. 시간은 아래에 보조로 제시했습니다.


### 한계와 마무리 · 25장

**25장**  문서 여섯 개와 모의 지표의 결과라 실제 장애 진단 성능으로 일반화할 수 없습니다. 검색은 지연과 오검색을 추가하고, 원문 출력은 종합 설명을 제한합니다. 이번에는 조사와 답변의 근거를 맞추는 데 집중했고, 다음에는 실제 로그와 새로운 질문으로 검증하겠습니다. 감사합니다.

## 상세 해설

사례를 이해하고 추가 설명이 필요할 때 활용한다. PPT 발표자 노트의 ‘상세 해설’에도 같은 내용을 넣었다.

### 2장 · 실습 1: 기존 장애 진단 에이전트 개선

사용자가 자연어로 장애를 설명하면 에이전트가 질문을 분류하고 조사 계획을 세운다. MCP로 상태 지표와 매뉴얼을 가져온 뒤 보고서를 만들며, 웹 화면에는 진행 과정과 최종 답변이 보인다. 이 기본 구조와 SQLite 대화 이력은 수업에서 제공됐다. 이번 작업은 새로운 모니터링 시스템을 만든 것이 아니라, 이 흐름에서 조사와 보고가 잘못되는 부분을 고친 것이다. 수집 도구에는 실제 로그·서비스 의존 관계나 서버 조치 기능이 없으므로 근본 원인을 확인하거나 복구를 수행했다고 말할 수 없다.

### 3장 · 조사 대상과 답변 근거를 맞추는 네 가지 개선

네 개선은 서로 연결된다. 첫째 필요한 대상을 빠짐없이 조사하고, 둘째 이름을 모르면 잘못된 대상을 대신 조사하지 않는다. 셋째 실제 관측 상태로 검색 필요 여부를 결정하고, 넷째 보고에 넣을 대상·수치·문서·절차가 수집 결과에 있는지 확인한다. RAG는 매뉴얼을 찾는 방법을 추가한 것이고, 상태 분기는 매뉴얼을 찾아야 하는 대상을 정하는 개선이다. 근거 화면과 비교 실행기는 이 처리가 사용자에게 보이고 반복해서 확인되도록 추가했다.

### 4장 · 개선 1 전: cache 조회 없이 공통 원인을 추정

원본 캡처에서 요청에는 payments-service와 cache-service가 모두 있지만 최종 프롬프트의 수집 사실에는 payments만 있다. 캐시의 상태를 확인하지 않고 두 서비스의 공통 원인을 추정한 것이 문제다. 모델의 가설을 실제 관측과 같은 수준으로 받아들이기 쉽다는 점에서 위험하다. 단순히 답변을 짧게 바꾸거나 프롬프트에 누락 금지를 쓰는 대신 실제 조회 작업 목록을 코드에서 결정하는 방향을 선택했다.

### 5장 · 개선 1 후: 요청한 서비스로 조회 목록을 구성

요청의 등록 서비스 전체를 추출하고, 모델이 제안한 tasks를 실행 권한의 기준으로 삼지 않는다. 확정된 대상마다 모니터링 작업을 다시 만들기 때문에 계획에서 빠진 서비스도 조사한다. 수집은 대상별로 수행하며 한 조회의 실패는 다른 대상의 결과와 분리해서 기록한다. 화면에서 확인할 것은 계획 문장에 서비스가 적혔는지가 아니라 실제 조회 목록에 두 서비스가 있고 각각 관측 결과가 반환됐는지다.

### 6장 · 개선 1 후: 공통 원인은 미확인으로 표시

캐시까지 조회했다는 것은 조사 범위 누락이 해결됐다는 증거다. 그러나 두 서비스의 저하가 같은 원인이라는 증거는 아니다. 현재 도구가 공유 DB, 배포 시점, 트래픽 추이, 호출 로그를 조사하지 않으므로 공통 원인은 미확인으로 남긴다. 개선의 성과는 원인을 더 많이 만들어낸 것이 아니라 확인한 사실과 더 조사해야 할 항목을 구분한 데 있다.

### 7장 · 개선 1 전: gateway만 조회

이 질문은 서로 연결된 두 서비스도 전부 조사하는지 확인하는 추가 사례다. 원본의 네트워크 매뉴얼 선택 자체를 오류라고 주장하는 것이 아니다. 상대 서비스인 payments의 상태를 수집하지 않은 것이 대상 누락 문제다.

### 8장 · 개선 1 후: 요청을 주고받는 양쪽을 조사

새로운 별도 알고리즘을 만든 사례가 아니라 앞의 대상 추출과 작업 재구성 처리를 다른 질문에 적용한 사례다. 두 서비스의 실제 조회가 나오는지 보면 같은 개선이 특정 한 문장에만 맞춘 수정인지 확인할 수 있다.

### 9장 · 개선 1 후: 두 서비스의 결과와 근거를 함께 제시

gateway의 네트워크 알림과 payments의 CPU 알림은 서로 다른 관측이다. 둘 다 확인됐더라도 CPU 급증 때문에 타임아웃이 발생했다고 확정하려면 시간적 관계와 실제 호출 자료가 추가로 필요하다. 따라서 서비스별 관측과 참고 매뉴얼을 제시하고 공통 원인 규명과는 구분한다.

### 10장 · 개선 2 전: billing을 물었는데 auth를 조회

원본의 auth 기본값은 기존 코드에 있던 정책이다. billing이 미등록일 때 인증 서비스로 대체되면서 요청과 조사 대상이 달라졌다. 기존 명세를 위반한 버그라고 단정하기보다, 장애 진단에서 임의 대체를 허용하지 않도록 정책을 변경했다고 설명한다.

### 11장 · 개선 2 후: 미등록 서비스는 이름부터 확인

미등록 이름을 발견하면 등록된 다른 이름으로 조용히 바꾸지 않는다. 조사 가능한 대상이 없을 때에는 계획·모니터링·보고 생성을 생략하고 확인 안내를 반환한다. 등록 대상과 미등록 대상이 섞여 있으면 등록된 대상은 조사하고 미등록 항목은 별도로 알린다. 이 안내를 장애 진단 성공으로 해석해서는 안 된다.

### 12장 · 개선 2 전: 서비스 이름 없이 auth를 조회

로그인이라는 증상은 인증 서비스를 연상시키지만 시스템마다 명칭과 경로가 다르다. 사용자가 실제로 요청한 서비스 이름이 없으면 auth라고 확정할 근거가 부족하다. 이름이 없을 때도 같은 기본값 제거 정책을 적용했다.

### 13장 · 개선 2 후: 서비스 이름을 먼저 확인

확인 질문이 한 번 늘어나 편의성은 낮아진다. 대신 잘못된 서비스의 상태를 가져와 사용자의 문제를 진단한 것처럼 보이는 일을 줄인다. 현재 구현은 등록된 서비스명을 명시하도록 요청하며 자연어 별칭을 자동으로 서비스 ID로 확정하는 기능은 추가하지 않았다.

### 14장 · 개선 3 전: 정상인 web에 DB 장애 매뉴얼 연결

원본에서 web-01은 healthy, CPU 41.0%, 알림 0건인데 DB Down 매뉴얼이 붙었다. 사용자가 CPU 급증이라고 말한 것과 실제 관측 상태가 다르므로 둘을 구분해야 한다. 이 질문은 auth 누락도 함께 드러내지만 여기서는 정상 서비스에 불필요한 장애 문서를 붙이는 문제에 집중한다.

### 15장 · 개선 3 후: 서비스별 상태에 맞는 매뉴얼 선택

서비스별로 유효한 상태와 수치, 활성 알림을 확인해 정상·장애 조사·정보 부족 등을 나눈다. 정상이나 정보 부족은 장애 문서를 임의로 붙이지 않는다. 조사 대상만 해당 서비스의 실제 알림으로 검색한다. web은 정상으로 남고 auth는 지연 매뉴얼을 받는 결과가 핵심이다. 어떤 매뉴얼이든 하나 반환하는 것을 검색 성공으로 세지 않는다.

### 16장 · 개선 4 전: 조회하지 않은 로그를 분석한 것처럼 답변

원본 최종 프롬프트에 특이 패턴 없음이라는 문장이 있지만 실제 로그를 조회한 도구 기록은 없다. 수집 도구가 제공하지 않는 분석을 검수에서도 통과시킨 것이 문제다. CPU 수치가 높다는 관측과 원인·조치가 확인됐다는 해석은 별개다.

### 17장 · 개선 4 후: 수치와 절차를 검증한 뒤 답변

모델이 자유로운 최종 보고서를 그대로 쓰게 하지 않고 서비스, 수치, 매뉴얼 ID, 절차 ID를 구조화해서 선택하게 했다. 코드가 대상 누락·중복, 수치 변경, 문서와 절차의 불일치를 확인한다. 통과한 매뉴얼 절차는 원문으로 출력하므로 CPU가 특정 기준을 넘고 지속될 때라는 조건이 완료 사실로 바뀌는 일을 줄인다. 이것은 자유 문장 전체의 의미를 판정하는 검증기가 아니며, 조치를 실행하거나 실행 여부를 확인하는 기능도 아니다. 원문 출력의 제한은 마지막 트레이드오프와 연결된다.

### 18장 · 대화 개선 전: 사용자 이름을 자기소개에 사용

기본 회귀 질문에는 장애 요청 외에 일반 대화도 포함된다. 사용자가 이름을 말한 뒤 다음 메시지로 이름을 물었을 때, 원본은 사용자 이름을 자신의 자기소개에 사용했다. 이 사례는 주요 개선 네 개와 구분한 대화 처리 보완이다.

### 19장 · 대화 개선 후: 사용자가 밝힌 이름으로 답변

대화 이력에서 사용자 역할의 직접적인 이름 선언만 읽고 가장 최근 선언을 사용한다. 질문이나 비서 자신의 문장은 이름의 출처로 사용하지 않는다. 기존 SQLite 이력을 사용하며 새 장기 메모리 저장소를 개발한 것은 아니다.

### 20장 · 개선에 적용한 기술

대상 확인·수집·검색·보고·검증의 책임을 나눠 기존 LangGraph 노드에 연결했다. MCP 서버에는 매뉴얼 검색 Tool을 추가하고 기존 Resource 원문 읽기를 재사용한다. 검색기는 기존 의존성 구조에 추가했으므로 실행 노드가 특정 검색 구현에 묶이지 않는다. 실제 앱에서는 MCP를 호출하고, 고정 비교 평가에서는 같은 입력과 관측이 유지되는 어댑터를 사용한다. 새 전문 Multi-Agent 시스템이나 새 LangSmith 분석을 구현했다고 주장하지 않는다.

### 21장 · 추가 1: 증상에 맞는 매뉴얼을 RAG로 검색

runbook 여섯 개의 본문과 한영 증상 메타데이터를 bge-m3로 임베딩하고 SQLite에 벡터를 캐시한다. 실제 서비스의 활성 알림도 벡터화한 뒤 코사인 유사도로 비교한다. 기준값 0.35를 넘는 후보 중 첫 문서의 URI로 MCP Resource 원문을 읽는다. 문서 내용이 바뀌면 digest로 캐시 갱신을 판단한다. 여섯 문서를 전수 비교하는 규모이므로 대규모 벡터 DB의 처리량을 검증했다고 말하지 않는다. 화면의 0.673은 관련도 점수다.

### 22장 · 추가 2: 답변에 사용한 근거를 함께 표시

조회 결과에서 서비스, 관측 수치, 매뉴얼, 미등록 대상, 미확인 항목을 별도 근거 객체로 만든다. 서버가 답변과 함께 보내고 웹이 그 객체를 표로 표시한다. 모델이 작성한 출처 문장을 다시 근거로 보여주는 방식과 다르다. 관측 자료가 없거나 검색을 생략한 이유가 드러나므로 사용자가 보고서 내용을 확인할 수 있다.

### 23장 · 추가 3: 같은 질문으로 전후 결과를 자동 비교

회귀 테스트는 코드가 바뀌어도 대상 추출이나 수치 검증 같은 핵심 분기가 유지되는지 확인한다. 서른한 개 단위 테스트의 기록이 있다. 별도로 원본과 개선판에 같은 질문 스무 개, 같은 고정 지표, 같은 모델 구성을 적용해 실행 기록을 남겼다. 화면은 그 기록을 모은 보고서다. 매뉴얼 검색 임베딩은 실제로 실행했지만 모니터링은 고정 어댑터를 사용하므로 실제 운영 네트워크 지연 시험은 아니다.

### 24장 · 정확성 평가: 조사 대상과 매뉴얼 선택

첫 지표의 분모 스무 건은 문항들에서 기대한 서비스 조회의 합계이며 서로 다른 서비스 스무 종류라는 뜻이 아니다. 세 번 누락됐던 조회가 보완됐다. 둘째는 질문마다 실제 조회 대상 집합이 기대 대상 집합과 완전히 같은지 비교해 스무 문항 중 열다섯 개에서 스무 개로 바뀐 것이다. 미등록·대상 없음에서 auth를 조회하지 않는 새 정책도 포함한다. 셋째는 정답 문서가 하나로 정해진 열두 문항에서 첫 문서 선택을 비교한 것이다. 전체 보고서의 의미적 진단 정확도를 직접 평가한 결과는 아니다. 시간은 전후 모두 완료한 같은 열여섯 문항의 중앙값 35.94초와 4.45초다. 생성 설정과 출력 형식도 바뀌었으므로 RAG만의 속도 개선으로 해석하지 않는다.

### 25장 · 한계와 다음 개선 방향

기능의 방향은 조사 범위와 보고 근거를 확인 가능하게 하는 것이다. 지금은 작은 문서 집합과 이미 관찰한 고정 질문을 사용하므로 새로운 질문과 운영 자료에서 별도 검증해야 한다. 임베딩·검색은 지연과 오검색을 더하고, 원문 절차 출력은 조건 보존에 유리하지만 복잡한 상황을 종합해서 설명하기 어렵다. 다음에는 실제 로그·시계열·의존 관계를 수집하고 독립 질문으로 선택과 원인 설명을 함께 평가해야 한다.

## 예상 질문

- **정확성이란 무엇을 측정했나?** 필요한 등록 서비스 조회, 조회 대상 집합 일치, 단일 정답 매뉴얼의 첫 선택을 각각 평가했다. 전체 원인 진단이나 자유 문장 전체의 의미 정확도를 측정한 수치는 아니다.
- **100%를 일반화할 수 있나?** 서비스 조회20건·범위20문항·문서12문항의 작은 고정 평가 세트 결과다. 운영 데이터와 독립 질문으로 추가 검증해야 한다.
- **왜 속도를 줄였나?** 속도도 같은16문항의 중앙값으로 보조 제시하지만, 핵심 성과는 조사 누락과 잘못된 대상·문서 선택을 줄인 것이다. 생성 설정·출력 형식도 바뀌었으므로 RAG 단독 속도 효과가 아니다.
- **어떤 기술을 직접 바꿨나?** MCP 검색 Tool·RAG·범위와 상태 분기·모듈화를 추가하고 기존 의존성 주입에 검색기를 확장했다. 전문 Multi-Agent·새 LangSmith 분석은 성과로 주장하지 않는다.
- **검증이 모델의 자유 문장 전체를 판단하나?** 서비스·수치·문서·절차 번호를 대조하고 선택한 절차 원문을 출력한다. 모든 문장의 의미나 자동 조치 조건을 판정하는 기능은 아니다.

## 발표 연습

먼저 본문만 소리 내어 읽고 화면을 넘기며 시간을 잰다. 5분을 넘으면 같은 대상 확인 처리를 반복하는7~9장과12~13장의 설명을 먼저 줄인다. 핵심 사례의 구현 방법, 선택 정확성 지표의 분모, 마지막 한계 설명은 남긴다. 관측 수치가 서로 다른 최초 화면과 재실행 화면의 숫자 차이를 개선 효과로 설명하지 않는다.
