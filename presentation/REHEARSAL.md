### 4장 · 사용 기술과 적용 방법

화면 지점: 기술별 적용 방법과 해결한 문제
대본 배분: 23초

**발표 대본**

MCP에 검색 도구를 추가하고 RAG로 문서를 찾습니다. 그래프 처리를 모듈로 분리하고 검색기를 주입해 실제 MCP와 고정 평가를 교체합니다. 분기 테스트와 동일 입력 평가로 확인했습니다.

**구현 설명·질문 대비**

- MCP: mcp_server.py의 search_runbooks Tool을 추가했다. retrieval.py의 MCPRunbookSearch가 이 Tool을 호출하고, research.py가 검색 결과의 URI로 기존 MCP Resource 원문을 읽는다. MCP 서버 분리나 기존 Tool·Resource 체계를 새로 구현한 성과로 주장하지 않는다.
- RAG: runbook 6개 본문·한영 증상 메타데이터와 서비스별 활성 알림을 bge-m3로 임베딩한다. SQLite에 캐시한 정규화 벡터의 코사인 유사도를 계산하고 임계값 0.35, 후보 2개 중 첫 원문을 연결한다. 대규모 벡터 DB나 ANN 검색을 구현한 것은 아니다.
- LangGraph·모듈화: 기존 graph.py의 단일 research 처리를 targets.py·research.py·retrieval.py·reporting.py·validation.py 등으로 나눴다. scope와 retrieve 노드 및 상태별 분기를 추가하고 검증 반복을 최대 두 번으로 제한했다. 독립적인 전문 Multi-Agent 서브그래프를 추가한 구현은 아니다.
- 의존성 주입: 기존 SupervisorDeps에 searcher를 추가했다. 연구 노드는 검색 구현을 직접 만들지 않고 주입된 검색기를 우선 사용한다. 실제 앱은 MCP 검색 Tool, 평가·단위 테스트는 고정 데이터 검색 어댑터를 연결한다.
- 단위 테스트 31개와 실제 모델 고정 입력 20건은 목적이 다르다. 전자는 대상 추출·수치 변조·부분 실패·시간 제한 등의 코드 분기, 후자는 실제 호출·문서 선택·응답 상태·시간을 확인한다. 실제 MCP·SSE·UI 검증은 별도로 수행했다.
- 교수님이 나열한 기술은 예시이며 전부 추가하라는 필수 목록으로 쓰여 있지 않다. 기존 LangSmith traceable 장식은 유지하지만 새 추적 연결·대시보드 분석을 검증한 성과에는 포함하지 않는다. 전문 Multi-Agent 확장도 성과로 표기하지 않는다.

## 예상 질문

- **지표 값이 전후에 다른 이유는?** 시연은 서로 다른 시점의 교육용 모의 지표다. CPU 하락을 개선 성과로 비교하지 않는다. 수치 평가는 같은 질문·고정 지표로 따로 실행했다.
- **RAG란?** 질문·관측에 맞는 문서를 검색해 답변의 참고 자료로 연결하는 방식이다. 이번에는 알림과 문서를 bge-m3로 임베딩하고 SQLite에서 코사인 유사도로 검색했다.
- **MCP는 어디에 썼나?** 모니터링 Tool과 매뉴얼 Resource의 연결에 사용했다. 원래 MCP를 활용하면서 매뉴얼 검색 Tool과 검색 의존성을 추가했다.
- **의존성 주입과 모듈화는?** 대상 식별·수집·검색·보고·검증을 분리했다. 기존 SupervisorDeps에 검색기를 주입하도록 확장해 검색 구현과 테스트 대역을 교체한다.
- **모델이 최종 문장을 모두 쓰나?** 모델은 수치·문서·절차 번호를 구조화해 선택한다. 코드가 수집 근거와 검증하고 절차는 원문으로 표시한다. 확인·시간 초과·이름 응답은 코드 경로다.
- **20/20이면 전부 정답인가?** 아니다. 서비스 수집 수·조회 범위·문서 선택·응답 반환은 서로 다른 지표다. 응답 반환에는 확인·검증 실패 안내도 포함된다.
- **왜 빨라졌나?** 생성량·시간 상한·출력 형식·처리 분기를 함께 바꿨다. RAG만의 속도 효과를 분리한 실험은 아니다.
- **8초가 기본 제한인가?** 지연 시험에서만 8초다. 기본 전체 상한은 60초, 호출 상한은 25초다.
- **실제 복구도 하나?** 교육용 모의 지표로 조사·안내한다. 실제 로그를 수집하거나 서버 증설·재시작·롤백을 실행하지 않는다.

- **원래 계획한 것만 발표하나?** 주요 개선 5개·추가 기능 3개를 모두 구현·증빙과 연결했다. 이름 응답은 수업 회귀 확인 중 더 보완한 부분이다. 실행 시 기존 프로세스·DB 보존은 보조 변경으로 보고서에 정리했다.
- **대상 누락을 코드로 어떻게 막나?** 요청과 등록 목록에서 대상을 직접 추출한다. 모델 작업을 그대로 실행하지 않고 확정 대상별 조회 작업을 다시 구성하며 수집은 그 전체 목록을 순회한다.
- **검증은 원래도 있었나?** 원본은 30자 이상과 1) 포함 같은 형식 조건이며 3회 실패 뒤 강제 합격했다. 개선은 서비스·수치·문서·절차를 검사하고 최대2회 후 실패 안내로 전환한다.

- **기술을 전부 써야 하나?** PDF는 Multi-Agent·MCP·RAG·의존성 주입·LangSmith·모듈화·단위 테스트 등을 평가 예시로 든다. 이번에는 MCP 확장·RAG·기존 LangGraph 개선·의존성 주입 확장·모듈화·테스트를 실제 구현과 연결한다. 전문 Multi-Agent 확장과 LangSmith 추적 분석은 검증한 성과가 아니다.
- **왜 의존성 주입이 필요한가?** 연구 노드가 특정 검색 구현에 묶이지 않도록 SupervisorDeps.searcher를 받게 했다. 실제 앱은 MCP 검색, 고정 평가와 단위 시험은 검색 어댑터를 연결할 수 있다.
- **교수님 순서는 어디에 반영됐나?** 2장 주제·베이스, 3장 개선·추가 요약, 4장 사용 기술·적용, 5~26장 문제·구현·전후와 추가 기능 실제 화면, 27장 그래프·28장 측정 기준, 29장 한계다.

- **그래프의 값은 어디에서 왔나?** 보존된 전후 실행 기록40개에서 서비스·조회 범위·문서 선택·같은16문항의 중앙값을 재집계했다. build_presentation_metrics.py로 데이터와 출처 해시를 재생성한다. 새 모델 성능 평가를 실행한 것은 아니다.
- **그래프가 실제 화면을 대신하나?** 27장은 측정 기록을 시각화한 그래프이며 28장은 실제 집계 보고서 캡처다. 실제 대화의 질문·응답 캡처는 앞의 개선·추가 기능 장에 모두 유지한다.

## 발표 직전

27장에서 네 그래프의 변화만 짚고 28장에서는 같은 기록의 판정 기준이라는 점을 짧게 확인한다.29장에서 한계를 설명한다. 내부 코드 이름은 상세 질문이 있을 때 보충 노트를 참고한다.
