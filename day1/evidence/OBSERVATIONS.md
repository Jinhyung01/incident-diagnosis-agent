# 사용자 실행에서 확인한 개선 전 사례

근거: 이 대화에 첨부된 캡처 7장, 사용자가 붙여 넣은 프롬프트·답변, 프로젝트 SQLite 대화 기록.

## 보존 상태

- 이전 보존 기록에는 TemporaryItems 경로가 없다고 적혀 있었다. 2026-10-22에는 사용자가 명시한 원본 파일 경로 7개를 직접 읽어 `user-screenshots/`에 바이트 변경 없이 보존했다. 해시는 `screenshot_inventory.json`에 기록했다. 디렉터리 목록 권한과 개별 파일 접근을 혼동하지 않는다.
- 현재 story PPT는 최초 사용자7장을 모두 본편·부록에 수록하고, 같은 질문의 개선 화면을 다음 장에 배치한다. 최초 캡처와 고정 지표 재실행의 수치를 같은 실행으로 취급하지 않는다.
- `session_transcript.local.json`은 기존 DB를 읽기 전용으로 연 대화 백업이다.
- DB에는 원본 프롬프트·실행 이벤트·수치 측정 시간이 저장되지 않으므로 캡처와 동일한 완전한 실행 기록은 아니다.
- `.local.json`은 개인 대화 기록이므로 기본 Git 추적에서 제외한다.
- 새로 실행하는 통제 실험은 별도 결과 파일에 질문·프롬프트·수집 근거·이벤트·시간을 저장한다.

## 관찰과 해석

| 캡처 | 요청 | 관찰 | 개선 필요 |
|---|---|---|---|
| 1 | gateway → payments 타임아웃 | gateway만 수집, network-timeout 매뉴얼 사용 | 상대 서비스도 조회해야 하는 요청 범위 검증 |
| 2 | payments CPU 급증 | payments 조회와 CPU 매뉴얼 사용, 로그 분석 결과라고 표현 | 데이터 종류에 맞는 주장인지 검증 |
| 3 | web-01 + auth | web-01만 조회, healthy·알림 없음에도 db-down 선택 | 일부 대상 누락과 기본 매뉴얼 강제 선택 제거 |
| 4 | payments + cache 공통 원인 | payments만 수집, cache를 포함한 원인 추정 생성 | 두 대상의 근거 확보 전 공통 원인 판단 제한 |
| 5 | 로그인 지연 | 이름이 없는 요청을 auth로 가정 | 등록된 별칭 없이 대상 단정 금지, 확인 요청 |
| 6 | billing 지연 | auth 조회로 대체 | 미등록 대상임을 표시 |
| 7 | 이름 기억 | 이력에 민수가 있어도 에이전트 자기 이름처럼 답함 | 역할 구분 및 응답 검증 |

7장만으로 전체 시스템의 오류율을 계산하지 않는다. 원인 가설은 코드와 통제 실험으로 확인한다.

## 별도 코드 확인

- 원본 plan의 복구는 research 0개일 때만 수행되며 일부 누락을 검사하지 않는다.
- 원본 분류는 키워드가 없으면 db-down을 선택한다.
- 원본 validate는 길이와 번호 형식만 검사한다.
- 첫 monitoring 호출의 타임아웃은 의도된 실습 장치다.
- 원본 실행 스크립트는 서버 재기동 전에 session.db를 삭제한다.
