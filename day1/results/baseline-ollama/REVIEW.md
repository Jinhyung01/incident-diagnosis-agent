# 개선 전 응답의 근거 대조 메모

작성: 2026-10-20, Codex의 AI 보조 검토. 사람의 최종 판정은 아직 수행하지 않았다. 정확도 점수를 산출한 문서가 아니며, 발표 전에 각 JSON의 `turns[].result.final`, `collected`, `last_prompt`를 직접 확인한다.

## 우선 수정할 사례

| 사례 | 실행 기록에서 확인한 사실 | 개선 방향 |
|---|---|---|
| D05 | gateway와 payments 요청에서 gateway만 조회. 답변은 네트워크 경로 이상을 가능성으로 표현했으나 payments 상태는 미확인 | 계획·수집 단계에서 요청 대상 전체 대조 |
| D06 | payments와 cache 요청에서 payments만 조회한 뒤 ReadTimeout | 누락 보완과 제한 시간 내 실패 응답을 각각 구현 |
| D07 | web만 조회하고 auth 누락. auth 정보 미수집은 밝혔지만 정상 web에 DB Down 매뉴얼을 검색 | 누락 인정에 그치지 않고 조회 시도; 정상 상태 기본값 제거 |
| D08 | billing 요청에서 auth 수치를 가져옴. `특이 패턴 없음`을 리전·인스턴스 집중 현상 없음으로 확대 | 미등록 대상을 알리고, 관측 범위를 넘는 주장 제한 |
| D09 | 대상 없는 로그인 요청을 auth로 처리하고 DB 연결 지연의 원인을 단정 | 별칭 정책을 명시하거나 대상 확인; 관측과 원인 분리 |
| D02 | 메모리 89%인데 즉시 재시작을 권고. 매뉴얼 조건은 90% 이상 | 조치 조건을 수치·연산자와 함께 보존 |
| D04 | 관측치 92%를 `92% 초과`로 표현. 매뉴얼의 조치 임계치는 90% | 관측값과 임계값을 별도 필드로 관리 |
| E02 | 메모리 89%에 즉시 재시작 권고. 구체적 힙 덤프 없이 캐시 증가·커넥션 미반환 등의 패턴이 존재한다고 서술 | 중간 LLM 분석을 검증된 관측 사실로 취급하지 않기 |
| E03 | 패킷 손실과 지연의 인과관계를 단정하고, 타임아웃이 너무 짧은지 확인 없이 상향 권고 | 원인 후보와 조건부 권고를 구분 |
| M02 | 두 번의 독립 요청을 같은 평가 세션에 전달했지만 `저의 이름은 민수입니다.`로 응답 | 사용자/assistant 역할 구분; 핵심 장애 진단 구현 후 선택 확장 |

## 잘 동작한 부분과 남는 조건

| 사례 | 관찰 |
|---|---|
| D03 | 디스크 사용률 95%에 disk-full 매뉴얼을 선택하고 정리 절차를 안내했다. 실제 파일 삭제를 실행했다는 기록은 없다. |
| D10, E05 | DB Down 매뉴얼을 불필요하게 검색했지만 최종 응답은 정상 상태이며 해당 절차가 적용되지 않는다고 설명했다. 검색 오류와 최종 답변 오류를 구분해야 한다. |
| D12 | 현재 CPU 89.1%에 즉시 증설을 권하지 않고 로그 확인이 필요하다고 안내했다. 다만 매뉴얼의 `90% 초과`를 `90% 이상`으로 바꿨으며, 알림 91%와 현재 값의 차이·지속 시간 미확인은 명시하지 않았다. |
| E04 | DB 장애 알림에 db-down을 선택했다. failover는 안내 절차이며 실행 완료 증거가 아니다. |
| E06 | 등록된 payments만 조회하고 billing 정보가 없다고 밝혔다. billing의 미등록 여부와 사용자에게 필요한 확인 질문은 더 명확히 할 수 있다. |
| M01 | 일반 인사는 장애 진단 도구를 호출하지 않고 처리했다. 표현이 어색하지만 핵심 장애 진단 개선의 우선순위는 낮다. |

## 시간 초과와 해석 범위

- D01, D06, D11, E01에서 약 303~307초 뒤 `ReadTimeout`이 발생했다.
- 이 사례들은 조회 대상·매뉴얼 호출 기록이 있으나 최종 답변이 없다. 조회 성공을 최종 응답 성공으로 계산하지 않는다.
- 오류 기록만으로 특정 내부 LLM 호출의 실패 원인을 확정하지 않는다. 내일 호출 단계별 시간·오류 기록을 추가하고 생성량·시간 상한을 설계한다.
- 실패한 호출은 Ollama 토큰 사용량을 반환하지 않았으므로 해당 사례의 토큰 합계는 부분 기록이다.
- D09의 추가 확인 기대값은 프로젝트에서 정한 정책이다. 등록된 `로그인 → auth-service` 별칭을 도입한다면 별칭 조건을 공개하고 평가 기대값 변경을 별도로 기록한다.
- 평가용 E01~E06은 기준 결과를 관찰했지만 검색 기준·프롬프트 조정에는 사용하지 않는다. 개발용 D01~D12로 구현을 조정하고, 평가용 결과를 본 뒤 다시 조정한다면 새 평가 질문을 추가한다.
- 고정 데이터 어댑터를 쓴 각 1회 실행이다. 실제 MCP 전송, 웹 UI, 실제 운영 환경의 성능을 대표하지 않는다.
